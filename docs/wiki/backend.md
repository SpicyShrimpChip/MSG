# 백엔드 교훈

> 초안: 커밋 기록과 `docs/backend-design.md`에서 정리했다. 주미 님이 확인하고 고치거나 더하는 곳이다.

## 머지된 마이그레이션은 고치지 않고 새 버전을 추가한다 (2026-10-27, #57)

- 상황: 공지 본문 컬럼을 추가해야 했다(`V3__add_notice_content.sql`).
- 원인: Flyway는 이미 적용된 `V*` 파일을 다시 검사한다. 파일을 고치면 이미 만든 DB와 맞지 않는다.
- 해결: 표 구조는 마이그레이션 파일로만 바꾼다. 적용된 `V*` 파일은 건드리지 않고 새 번호를 추가한다.
- 다음에는: 새 버전 번호는 둘이 겹치지 않게 미리 말한다(지금 다음 번호는 `backend/CLAUDE.md` "DB 마이그레이션"). 로컬 DB가 꼬이면 지우고 다시 켠다.

## 앱 DB 계정과 마이그레이션 계정을 나눈다 (2026-10-25, 초기 환경 구축)

- 상황: 로컬 DB를 만들 때 계정을 어떻게 둘지 정했다.
- 해결: 앱 계정은 데이터 읽기·쓰기만 하고, 표 변경은 마이그레이션 계정만 한다(`application-local.yaml`).
- 다음에는: 운영 DB 호스팅을 고를 때 이 두 계정을 만들 수 있고, 표 만들기 권한이 막히지 않는지 확인한다.

## 역할은 토큰이 아니라 요청마다 DB에서 읽는다 (2026-10-27, #56)

- 상황: 관리자 전용 경로(`/api/admin/**`)를 만들었다.
- 원인: 토큰에 역할을 고정하면 역할을 바꿔도 이미 발급된 토큰은 그대로 통한다.
- 해결: 세션 확인(`SessionValidator`)이 살아 있는 세션의 역할을 함께 돌려주고, 인증 필터가 그 역할을 권한으로 쓴다. 역할을 바꾸면 같은 토큰도 바로 403이 된다(통합 테스트로 확인).
- 다음에는: 가입은 항상 `USER`이고 관리자는 DB에서 직접 지정한다(역할 변경 API 없음). 화면 숨김은 보안이 아니다.

## 탭 두 개가 동시에 로그인을 연장하면 둘 다 로그아웃된다 (2026-11-24, #211)

- 상황: 같은 쿠키로 `/api/auth/refresh`를 동시에 두 번 보내면 하나는 401이 되고, 재사용 감지가 세션을 끊어 모든 탭이 로그아웃됐다. 로컬은 왕복이 짧아 잘 안 겹친다.
- 원인: 한 탭 안의 갱신만 하나로 묶었고, 늦게 온 정상 요청도 "폐기된 토큰 재사용"과 구별하지 않았다.
- 해결: 서버는 회전된 지 10초 안이고 세션이 살아 있으면 한 번 더 회전한다(`app.auth.refresh-reuse-grace`). 프론트는 Web Locks로 탭끼리 차례를 지킨다. 동시 요청 통합 테스트(`AuthApiTest`)는 유예를 0으로 두면 실패한다.
- 다음에는: 토큰을 하나씩 폐기하는 기능을 더하면 "세션이 살아 있음 = 회전으로 폐기됨" 판단이 깨진다. 그때는 폐기 사유 칸을 추가한다.

## 공지 본문은 HTML로 해석하지 않고 글자 그대로 저장한다 (2026-10-27, #57)

- 상황: 관리자가 쓴 공지 본문을 사용자 화면에 보여 준다.
- 해결: 제목 100자·본문 5000자로 검증하고 앞뒤 공백을 지운 뒤, HTML로 해석하지 않고 글자 그대로 저장한다. 프론트도 글자로만 다룬다.
- 다음에는: 작성자는 요청 본문이 아니라 토큰의 사용자로 정하고 응답에는 내보내지 않는다. 작성자가 탈퇴해도 공지는 남도록 `ON DELETE SET NULL`로 두었다.

## MySQL에서 PostgreSQL로 옮길 때 H2 테스트를 지키는 법 (2026-10-30, #78)

- 상황: 10/28 멘토링 추천으로 DB를 PostgreSQL + pgvector로 바꿨다. 빠른 기본 테스트는 H2로 유지하고 싶었다.
- 원인: `CREATE EXTENSION vector`는 H2에서 실패한다. `AUTO_INCREMENT`·`DATETIME(6)`·`FROM DUAL`은 PostgreSQL 문법이 아니다.
- 해결: 공통 문법(`GENERATED BY DEFAULT AS IDENTITY`, `TIMESTAMP(6)`)으로 마이그레이션을 쓰고, H2는 `MODE=PostgreSQL`로 둔다. 확장 설치는 `db/vector/`로 분리해 local·prod 프로필의 Flyway `locations`에만 넣는다. `vector`는 슈퍼유저만 만들 수 있어 DB 준비 단계(스크립트·CI)에서 미리 설치한다.
- 예외: 이번에는 운영 DB가 없어서 마이그레이션을 Postgres 문법으로 다시 썼다("머지된 마이그레이션은 고치지 않는다"의 예외). 처음에는 V1~V3을 문법만 고쳤다가 10/31에 `V1` 하나로 합쳐 처음부터 다시 시작했다(#82). 각자 로컬 DB를 새로 만들어야 하고, 운영 DB가 생기면 이렇게 하지 않는다. 11/24에 첫 운영 배포 직전 한 번 더 V1~V16을 V1 하나로 합쳤다: 합치기 전 16개와 새 V1을 빈 DB 두 개에 각각 적용해 `pg_dump --schema-only`로 비교해 같은 것을 확인했고(나중에 더한 열은 표 끝에 둬 열 순서까지 같게), 로컬 DB는 비우고 다시 만들었다. 운영 DB를 만든 뒤로는 더는 합치지 않는다.
- 다음에는: 버전 번호를 `V0_1`로 두어야 나중에 추가하는 V2 이상과 순서가 꼬이지 않는다. 실제 DB 동작은 `./gradlew pgTest`와 CI의 `postgres-test`로 확인한다.

## 긴 글에 쓰는 정규식이 1MB 요청 하나를 몇 분 동안 붙잡는다 (2026-11-01, #96)

- 상황: 대화 가져오기 서버 개인정보 재검사에 프론트 `mask.ts`의 이메일 정규식을 그대로 옮겼더니, 메시지 20,000자 × 50개 테스트 하나가 283초 걸렸다.
- 원인: `[A-Za-z0-9._%+-]+@...`는 '@'가 없는 긴 영문·숫자 덩어리(코드, 붙여 넣은 글)에서 시작 위치마다 끝까지 읽고 되돌아가서 글 길이의 제곱만큼 돈다.
- 해결: 앞에 `(?<![A-Za-z0-9._%+-])`를 붙여 덩어리 맨 앞에서만 시작하고, `++`(되돌아가지 않음)로 바꿨다. 찾는 결과는 같다. 같은 글 1MB 검사가 0.5초 안으로 줄었다.
- 다음에는: 사용자 글 전체에 돌리는 정규식은 아주 긴 한 글자 반복(`"a".repeat(20000)`)으로 시간 테스트를 넣는다. 프론트 `mask.ts`의 같은 정규식도 브라우저에서 같은 문제가 날 수 있다.

## `@Enumerated(STRING)` 열로 정렬하면 enum 순서가 아니라 글자 순이다 (2026-11-01, #98)

- 상황: 분석 결과의 모델 목록을 `findAllByRunIdOrderByProviderAsc`로 읽었더니 GPT·CLAUDE·GEMINI가 아니라 CLAUDE·GEMINI·GPT 순으로 왔다.
- 원인: enum을 글자로 저장(`EnumType.STRING`)하면 DB 정렬은 글자 순이다. Java의 enum 선언 순서는 DB가 모른다.
- 해결: 조회는 정렬 없이 하고 Java에서 `Comparator.comparing(엔티티::getProvider)`로 enum 순서대로 정렬한다.
- 다음에는: 화면 순서가 중요한 enum은 정렬을 Java에서 하거나 순서용 숫자 열을 따로 둔다.

## 머지 전 마이그레이션을 고치면 `pgTest`가 Flyway 검증 오류로 모두 실패한다 (2026-11-02, #107)

- 상황: 새 `V6`으로 `pgTest`를 한 번 돌린 뒤 같은 파일의 표 이름을 바꾸고 다시 돌리자 모든 통합 테스트가 `FlywayValidateException`으로 멈췄다. H2 `test`는 통과했다.
- 원인: `msg_test`는 테스트 사이에 지워지지 않아 처음 적용한 `V6`의 체크섬이 `flyway_schema_history`에 남아 있다. H2는 매번 새로 만들어서 문제가 안 보인다.
- 해결: 테스트 DB에서만 그 버전의 표를 지우고 `DELETE FROM flyway_schema_history WHERE version = '6'` 후 다시 돌렸다. 서비스 DB(`msg`)에 적용했다면 같은 방법으로 로컬에서 되돌린다.
- 다음에는: 표 이름·열은 `pgTest` 전에 정한다. 머지된 번호라면 고치지 말고 새 번호를 쓴다(위 "머지된 마이그레이션은 고치지 않고").

## 응답에 새 필드를 더했더니 다른 사람의 계약 테스트가 깨졌다 (2026-11-03, PR 번호는 머지 때)

- 상황: 퀴즈 풀기 응답에 평가 개념 출처 `conceptSource`를 더하자 `QuizApiTest`의 "풀기 화면에는 정답·해설이 없다"가 실패했다.
- 원인: 그 테스트는 응답 글 전체에 `"concept"`라는 글자가 없는지 본다(문제별 개념 힌트를 막는 계약). 필드 이름에 그 글자가 들어갔다.
- 해결: 팀원 테스트는 고치지 않고 필드 이름을 `topicSource`로 바꿨다. 값(material/course)과 뜻은 그대로다.
- 다음에는: 풀기 응답(`QuizResponse`)에 필드를 더하기 전에 `QuizApiTest`의 금지 단어(correct, aiExplanation, 해설, concept)를 먼저 본다.

## 저장 직후 응답의 시각이 다시 읽은 값과 달라 Linux CI에서만 테스트가 깨진다 (2026-11-05, #123)

- 상황: 개념 학습 완료 API의 `firstCompletedAt`을 두 번 비교하는 테스트가 macOS에서는 통과했는데 CI(`build-and-test`, `postgres-test`)에서만 실패했다.
- 원인: Linux의 JDK 17은 `Instant.now()`가 나노초까지 나오고, DB 열(`TIMESTAMP(6)`)은 마이크로초까지만 저장한다. 저장 직후 응답은 메모리의 나노초 값을, 다시 읽은 응답은 잘린 값을 준다. macOS는 시계가 마이크로초라 차이가 안 보인다. 테스트 시계 `MutableClock`에 나노초를 더해 로컬에서 재현했다.
- 해결: 엔티티에 넣는 시각을 `LocalDateTime.now(clock).truncatedTo(ChronoUnit.MICROS)`로 DB 정밀도에 맞췄다.
- 다음에는: 저장 직후 응답으로 시각을 돌려주거나 비교하는 코드는 마이크로초로 자른다. CI에서만 깨지면 OS별 시계 정밀도부터 의심한다.

## 키를 넣었는데 퀴즈가 설정한 첫 모델이 아닌 다른 모델로 만들어진다 (2026-11-05, #132)

- 상황: LLM 키 3개를 넣고 퀴즈를 만들자 `generatedBy`가 GPT가 아니라 Gemini였다. 로그에는 `REJECTED`, 다음 시도에는 "배점이 범위 밖이다"가 남았다.
- 원인: ① `.env`의 `OPENAI_MODEL` 값 끝에 탭이 붙어 있었다(설정값은 끝 공백을 지우지 않는다). ② Anthropic은 키가 아니라 크레딧 부족으로 400을 줬다. ③ 지시문의 "배점(points, 2~5)"을 GPT가 합계로 읽어 기준 하나에 1점을 줬고, 서버 검증(기준마다 2~5)에 걸렸다.
- 해결: 탭을 지우고, 지시문을 "기준 하나하나 2~5 정수, 합계 아님"으로 고쳤다(`quiz-gen-v4`). 서술형 퀴즈를 GPT가 3번 모두 통과했다.
- 다음에는: 실패한 모델은 다음 모델로 넘어가 화면에서 안 보이니 `generatedBy`와 로그를 본다. `REJECTED`면 제공사 오류 메시지를 직접 확인하고, 지시문의 숫자 범위는 검증 코드와 같은 단위로 쓴다.

## 대화 하나가 길면 분석에서 통째로 빠져 "키워드가 들어간 대화가 없어요"가 뜬다 (2026-11-20, PR 번호는 머지 때)

- 상황: 키워드가 모든 턴에 들어간 50메시지짜리 공부 대화 하나만 가져와 분석하자 400 "과목 키워드가 들어간 대화가 없어 분석할 수 없어요"가 나왔다. 28,000자 대화는 통과해서 처음엔 재현이 안 됐다.
- 원인: `AnalysisInputBuilder`가 대화를 한 덩어리로 만들고, 전체 상한(`max-input-chars`)을 넘으면 그 대화를 `continue`로 건너뛰었다. 메시지 하나를 1,500자로 잘라도 메시지가 많으면 3만 자를 넘는다. 건너뛴 대화는 어디에도 세지 않아 오류 문구도 틀렸다.
- 해결: 상한을 넘는 대화는 최근 메시지부터 메시지 단위로 담고 빠진 앞쪽 메시지 수를 표시한다. 뒤에 담을 대화가 남아 있으면 대화 하나는 남은 자리의 절반까지만 쓴다(`AnalysisInputBuilderTest`).
- 다음에는: 상한을 넘는 항목을 통째로 버리는 코드는 그 항목이 하나뿐일 때 결과가 비는지 본다. 재현할 때는 잘린 뒤 길이(메시지 수 × 상한)로 계산한다.

## 반복문을 공용 도우미로 합쳤더니 개념 뽑기의 시간 초과 동작이 바뀌었다 (2026-11-21, #175)

- 상황: 퀴즈 만들기·자료 개념 뽑기·개념 설명의 "모델 차례 호출" 반복문 3개를 `QuizModelFallback` 하나로 합쳤다. 테스트 383개가 모두 통과했지만, 따로 맡긴 검토에서 동작이 달라진 곳이 나왔다.
- 원인: 퀴즈 만들기는 한 모델이 시간 초과면 바로 멈추고, 개념 뽑기·설명은 다음 모델로 넘어갔다(마감은 다음 반복에서 확인). 비슷해 보여서 도우미를 퀴즈 만들기 규칙 하나로 만들었다. `ModelInvoker.await`는 마감 조금 전에도 시간 초과를 돌려줄 수 있어 실제로 결과가 달라진다. 기존 테스트에는 이 경우가 없었다.
- 해결: 호출마다 고르게 `Call.stopOnTimeout`을 두고, 퀴즈 만들기는 true, 개념 뽑기·설명은 false로 원래 동작을 유지했다.
- 다음에는: 복사된 코드를 합치기 전에 원본들을 줄 단위로 비교해 `break`/`continue`·오류 코드 차이를 표로 적는다. 다르면 합치되 옵션으로 남긴다.

## AI 시간 예산이 프록시 한도보다 길면 배포 뒤 화면만 실패로 보인다 (2026-11-23, #197)

- 상황: 배포 구성(브라우저 → Vercel `/api` rewrite → EC2)을 짜다가, 분석·퀴즈 만들기 예산(150초)이 프록시 한도보다 긴 것을 발견했다. 로컬에는 프록시가 없어 드러나지 않았다.
- 원인: Vercel은 외부 백엔드의 첫 응답을 120초까지만 기다리고 504를 돌려준다. 서버는 계속 돌아 결과를 저장하는데 화면은 실패로 끝난다.
- 해결: 서버 예산을 모두 100초, 프론트 timeout을 115초(`AI_REQUEST_TIMEOUT_MS`)로 하고, 서버 응답 형식이 없는 504는 시간 초과로 다뤄 화면이 결과를 다시 확인하게 했다.
- 다음에는: 오래 걸리는 요청의 예산은 "서버 예산 < 프론트 timeout < 앞단 프록시 한도" 순서인지 본다. 프록시·호스팅을 바꾸면 그 한도부터 확인한다.

## NUL 문자가 든 대화가 "다른 요청과 겹쳐"(409)로 계속 실패한다 (2026-11-24, 이슈 #215)

- 상황: 코드 실행 결과를 붙여 넣은 대화처럼 NUL 문자(`\u0000`)가 든 글을 가져오면 묶음(최대 50개) 전체가 409로 실패했고, 다시 시도해도 같았다. 과목 이름 같은 다른 글 입력도 같았다. `./gradlew test`(H2)는 모두 통과했다.
- 원인: PostgreSQL 텍스트 칸은 NUL을 받지 않는데(`invalid byte sequence for encoding "UTF8": 0x00`) H2는 그대로 저장한다. 그 DB 오류(`DataIntegrityViolationException`)를 전역 예외 처리가 모두 "동시 요청 충돌"로 바꿨다.
- 해결: 들어오는 JSON 글자 값·요청 파라미터와 모델 답변(`LlmResponse`)에서 NUL만 지운다(`NulStrippingConfig`). 프론트 파서도 읽을 때 지운다. 409는 UNIQUE 위반(SQL 상태 23505)일 때만 쓰고, 나머지 DB 제약 위반은 다시 시도를 권하지 않는 400으로 바꿨다.
- 다음에는: 글자를 저장하는 새 입구(JSON이 아닌 본문, 파일에서 읽은 글 등)를 만들면 NUL을 지우는지 본다. DB마다 다른 동작은 H2 테스트로 잡히지 않으니 `./gradlew pgTest`로 확인한다.

## 모델이 모두 실패한 분석이 "최근 분석"이 되어 이전 결과를 덮었다 (2026-11-24, PR 번호는 머지 때)

- 상황: 모의 AI 서버로 세 모델 모두 오류를 내게 하고 다시 분석하자, 대시보드의 모든 개념이 "판단한 모델 없음"이 되고 "이 개념의 변화"에 가짜 변화가 남았다(#209). 분석 중 새로고침하면 "분석 중" 표시도 사라졌다(#214).
- 원인: `runs/latest`가 끝난 상태(`FAILED` 포함) 중 가장 최근 것을 돌려줬고, 숙련도 기록은 그 응답으로 계산해 남겼다. 진행 중인 분석은 응답에 없었다.
- 해결: `runs/latest`를 `{ run, lastAttempt }`로 바꿔 `run`은 모델이 판단한 분석만, 진행 중·실패한 시도는 `lastAttempt`로 따로 알린다. 숙련도 기록은 `failed`면 남기지 않고, `partial`은 퀴즈·산식이 바뀐 때만 남긴다.
- 다음에는: "가장 최근 결과"를 고를 때 실패한 실행이 결과 자리를 차지하지 않는지, 그 결과로 쌓는 기록(변화 추이)이 장애를 학습 변화로 남기지 않는지 본다.

## 테스트 공용 초기화의 설정값이 `@TestPropertySource`를 이겼다 (2026-11-24, 카카오 로그인)

- 상황: 통합 테스트가 모두 같은 가짜 카카오 서버를 쓰도록 `@IntegrationTest`의 초기화(`TestKakao`)에서 카카오 키를 넣었다. 키가 없을 때를 보는 테스트에 `@TestPropertySource(properties = "app.oauth.kakao.client-id=")`를 붙였는데 키가 그대로 남아 실패했다.
- 원인: 초기화(`ApplicationContextInitializer`)는 `@TestPropertySource`의 값이 환경에 들어간 뒤에 돈다. 초기화가 `addFirst`로 넣은 값이 맨 앞이 되어 테스트 클래스가 정한 값보다 먼저 읽혔다.
- 해결: 초기화는 `TestPropertySourceUtils.INLINED_PROPERTIES_PROPERTY_SOURCE_NAME`("Inlined Test Properties")이 있으면 그 **바로 뒤**에 넣는다. 테스트 클래스 값이 이기고, 그 밖의 설정·`backend/.env`보다는 앞이라 개발자 PC의 실제 키는 여전히 덮는다.
- 다음에는: 테스트 초기화에서 설정값을 넣을 때는 클래스별로 바꿔야 하는 값인지 먼저 보고, 그렇다면 인라인 값 뒤에 넣는다. `@DynamicPropertySource`는 클래스마다 컨텍스트를 새로 띄우니 공용 값에는 쓰지 않는다.

## 카카오는 동의하는 순간 연결된다: 가입을 거절하면 연결만 남는다 (2026-11-24, 카카오 로그인)

- 상황: 실제 카카오로 확인하다가, 탈퇴 직후 다시 카카오 로그인 → 재가입 제한으로 거절했더니 사용자의 카카오 "연결된 서비스"에 계정도 없는 MSG가 남았다.
- 원인: 카카오 앱은 기본으로 동의 화면에서 동의할 때 연결을 만든다. 우리 서버가 가입을 받을지는 그 뒤 콜백에서 정하는데, 계획에는 탈퇴 때만 연결 끊기를 넣었고 가짜 카카오 서버 테스트도 돌아가는 주소만 확인했다.
- 해결: 콜백에서 거절할 때(이메일 없음·확인 안 된 이메일·같은 이메일 계정 충돌·재가입 제한) 연결 끊기를 부른다(`SocialAuthController.handleOrUnlink`). 테스트에 연결 끊기 요청 수·회원번호 확인을 더했다.
- 다음에는: 외부 로그인은 "외부 쪽에 무엇이 언제 생기는지"를 먼저 적고, 우리 쪽에서 거절·실패하는 모든 갈래에서 외부 상태를 되돌리는지 본다. 가짜 서버 테스트는 응답뿐 아니라 외부로 나간 요청도 확인한다.

## 개발자 PC의 `backend/.env`에 키를 넣자 탈퇴 테스트가 로컬에서만 깨졌다 (2026-11-24, 이슈 #229)

- 상황: 맥 `backend/.env`에 `REJOIN_HASH_SECRET`을 넣은 뒤 `./gradlew test`에서 같은 이메일로 다시 가입하는 탈퇴 테스트가 409로 실패했다. CI는 `.env`가 없어 통과했다.
- 원인: `application.yaml`이 `optional:file:.env[.properties]`를 읽어 테스트에도 키가 들어가 재가입 제한이 켜졌다. AI·Turnstile·카카오 키는 테스트 초기화(`TestLlm`·`TestKakao`)가 덮었지만 이 키는 빠져 있었다.
- 해결: `TestLlm`이 `app.rejoin.hash-secret`도 비운다(인라인 테스트 값 뒤에 넣어 재가입 제한 테스트의 `@TestPropertySource`가 이긴다).
- 다음에는: 비우면 기능이 꺼지는 새 비밀 설정을 만들면 테스트 초기화에서도 비운다. 로컬에서만 깨지면 `.env` 값부터 의심한다.

## `afterCommit`에서 외부 API를 부르면 그동안 DB 연결을 잡는다 (2026-11-24, 이슈 #229)

- 상황: 탈퇴 뒤 카카오 연결 끊기를 `TransactionSynchronization.afterCommit`에서 불렀다(리뷰에서 지적).
- 원인: 스프링은 `afterCommit`·`afterCompletion`을 부른 **뒤에** 커넥션을 반납한다. 외부 응답이 느리면 그동안 풀의 연결 하나가 묶인다.
- 해결: 서비스는 끊을 회원번호만 돌려주고, 컨트롤러가 서비스(트랜잭션)가 끝난 뒤 `unlinkKakao`를 부른다(`open-in-view: false`라 컨트롤러에는 연결이 없다). 가짜 카카오 서버가 요청을 받는 순간 Hikari 풀의 빌려 간 연결 수가 0인지 테스트한다(예전 코드는 1).
- 다음에는: 커밋 뒤 외부 호출은 트랜잭션 콜백 말고 트랜잭션 메서드 밖(호출한 쪽)이나 비동기로 한다. 파일 삭제처럼 짧은 로컬 작업은 콜백도 괜찮다.

## 설정 record에 생성자를 하나 더 만들었더니 앱이 뜨지 않는다 (2026-11-24, feat/evidence-based-ai-learning)

- 상황: `MaterialContentProperties`(`@ConfigurationProperties` record)에 필드를 더하면서 테스트 편의용 3인자 생성자를 하나 더 만들었더니 통합 테스트 전체가 `No default constructor found`로 실패했다.
- 원인: record에 생성자가 둘 이상이면 스프링이 어느 생성자로 묶을지 정하지 못해 기본 생성자를 찾는다.
- 해결: 보조 생성자를 지우고 테스트에서 전체 인자를 넘긴다(기본값이 필요하면 압축 생성자 안에서 채운다).
- 다음에는: 설정 record는 생성자를 하나만 둔다. 꼭 둘이 필요하면 바인딩할 생성자에 `@ConstructorBinding`을 붙인다.

## 영문 개념 이름을 부분 문자열로 찾으면 다른 낱말 안에서도 잡힌다 (2026-11-24, feat/evidence-based-ai-learning)
