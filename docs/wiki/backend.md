# 백엔드 교훈

> 초안: 커밋 기록과 `docs/backend-design.md`에서 정리했다. 주미 님이 확인하고 고치거나 더하는 곳이다.

## 머지된 마이그레이션은 고치지 않고 새 버전을 추가한다 (2026-10-27, #57)

- 상황: 공지 본문 컬럼을 추가해야 했다(`V3__add_notice_content.sql`).
- 원인: Flyway는 이미 적용된 `V*` 파일을 다시 검사한다. 파일을 고치면 이미 만든 DB와 맞지 않는다.
- 해결: 표 구조는 마이그레이션 파일로만 바꾼다. 적용된 `V*` 파일은 건드리지 않고 새 번호를 추가한다.
- 다음에는: 새 버전 번호는 둘이 겹치지 않게 미리 말한다(지금 다음 번호는 `backend/CLAUDE.md` "DB 마이그레이션"). 로컬 DB가 꼬이면 지우고 다시 켠다.

## 앱 DB 계정과 마이그레이션 계정을 나눈다 (2026-10-25, 초기 환경 구축)

- 상황: 로컬 DB를 만들 때 계정을 어떻게 둘지 정했다.
- 해결: 앱 계정은 데이터 읽기·쓰기만 하고, 표 변경은 마이그레이션 계정만 한다(`application-local.yaml`).
- 다음에는: 운영 DB 호스팅을 고를 때 이 두 계정을 만들 수 있고, 표 만들기 권한이 막히지 않는지 확인한다.

## 역할은 토큰이 아니라 요청마다 DB에서 읽는다 (2026-10-27, #56)

- 상황: 관리자 전용 경로(`/api/admin/**`)를 만들었다.
- 원인: 토큰에 역할을 고정하면 역할을 바꿔도 이미 발급된 토큰은 그대로 통한다.
- 해결: 세션 확인(`SessionValidator`)이 살아 있는 세션의 역할을 함께 돌려주고, 인증 필터가 그 역할을 권한으로 쓴다. 역할을 바꾸면 같은 토큰도 바로 403이 된다(통합 테스트로 확인).
- 다음에는: 가입은 항상 `USER`이고 관리자는 DB에서 직접 지정한다(역할 변경 API 없음). 화면 숨김은 보안이 아니다.

## 공지 본문은 HTML로 해석하지 않고 글자 그대로 저장한다 (2026-10-27, #57)

- 상황: 관리자가 쓴 공지 본문을 사용자 화면에 보여 준다.
- 해결: 제목 100자·본문 5000자로 검증하고 앞뒤 공백을 지운 뒤, HTML로 해석하지 않고 글자 그대로 저장한다. 프론트도 글자로만 다룬다.
- 다음에는: 작성자는 요청 본문이 아니라 토큰의 사용자로 정하고 응답에는 내보내지 않는다. 작성자가 탈퇴해도 공지는 남도록 `ON DELETE SET NULL`로 두었다.

## MySQL에서 PostgreSQL로 옮길 때 H2 테스트를 지키는 법 (2026-10-30, #78)

- 상황: 10/28 멘토링 추천으로 DB를 PostgreSQL + pgvector로 바꿨다. 빠른 기본 테스트는 H2로 유지하고 싶었다.
- 원인: `CREATE EXTENSION vector`는 H2에서 실패한다. `AUTO_INCREMENT`·`DATETIME(6)`·`FROM DUAL`은 PostgreSQL 문법이 아니다.
- 해결: 공통 문법(`GENERATED BY DEFAULT AS IDENTITY`, `TIMESTAMP(6)`)으로 마이그레이션을 쓰고, H2는 `MODE=PostgreSQL`로 둔다. 확장 설치는 `db/vector/`로 분리해 local·prod 프로필의 Flyway `locations`에만 넣는다. `vector`는 슈퍼유저만 만들 수 있어 DB 준비 단계(스크립트·CI)에서 미리 설치한다.
- 예외: 이번에는 운영 DB가 없어서 마이그레이션을 Postgres 문법으로 다시 썼다("머지된 마이그레이션은 고치지 않는다"의 예외). 처음에는 V1~V3을 문법만 고쳤다가 10/31에 `V1` 하나로 합쳐 처음부터 다시 시작했다(#82). 각자 로컬 DB를 새로 만들어야 하고, 운영 DB가 생기면 이렇게 하지 않는다.
- 다음에는: 버전 번호를 `V0_1`로 두어야 나중에 추가하는 V2 이상과 순서가 꼬이지 않는다. 실제 DB 동작은 `./gradlew pgTest`와 CI의 `postgres-test`로 확인한다.

## 긴 글에 쓰는 정규식이 1MB 요청 하나를 몇 분 동안 붙잡는다 (2026-11-01, #96)

- 상황: 대화 가져오기 서버 개인정보 재검사에 프론트 `mask.ts`의 이메일 정규식을 그대로 옮겼더니, 메시지 20,000자 × 50개 테스트 하나가 283초 걸렸다.
- 원인: `[A-Za-z0-9._%+-]+@...`는 '@'가 없는 긴 영문·숫자 덩어리(코드, 붙여 넣은 글)에서 시작 위치마다 끝까지 읽고 되돌아가서 글 길이의 제곱만큼 돈다.
- 해결: 앞에 `(?<![A-Za-z0-9._%+-])`를 붙여 덩어리 맨 앞에서만 시작하고, `++`(되돌아가지 않음)로 바꿨다. 찾는 결과는 같다. 같은 글 1MB 검사가 0.5초 안으로 줄었다.
- 다음에는: 사용자 글 전체에 돌리는 정규식은 아주 긴 한 글자 반복(`"a".repeat(20000)`)으로 시간 테스트를 넣는다. 프론트 `mask.ts`의 같은 정규식도 브라우저에서 같은 문제가 날 수 있다.

## `@Enumerated(STRING)` 열로 정렬하면 enum 순서가 아니라 글자 순이다 (2026-11-01, #98)

- 상황: 분석 결과의 모델 목록을 `findAllByRunIdOrderByProviderAsc`로 읽었더니 GPT·CLAUDE·GEMINI가 아니라 CLAUDE·GEMINI·GPT 순으로 왔다.
- 원인: enum을 글자로 저장(`EnumType.STRING`)하면 DB 정렬은 글자 순이다. Java의 enum 선언 순서는 DB가 모른다.
- 해결: 조회는 정렬 없이 하고 Java에서 `Comparator.comparing(엔티티::getProvider)`로 enum 순서대로 정렬한다.
- 다음에는: 화면 순서가 중요한 enum은 정렬을 Java에서 하거나 순서용 숫자 열을 따로 둔다.

## 머지 전 마이그레이션을 고치면 `pgTest`가 Flyway 검증 오류로 모두 실패한다 (2026-11-02, #107)

- 상황: 새 `V6`으로 `pgTest`를 한 번 돌린 뒤 같은 파일의 표 이름을 바꾸고 다시 돌리자 모든 통합 테스트가 `FlywayValidateException`으로 멈췄다. H2 `test`는 통과했다.
- 원인: `ai_lms_test`는 테스트 사이에 지워지지 않아 처음 적용한 `V6`의 체크섬이 `flyway_schema_history`에 남아 있다. H2는 매번 새로 만들어서 문제가 안 보인다.
- 해결: 테스트 DB에서만 그 버전의 표를 지우고 `DELETE FROM flyway_schema_history WHERE version = '6'` 후 다시 돌렸다. 서비스 DB(`ai_lms`)에 적용했다면 같은 방법으로 로컬에서 되돌린다.
- 다음에는: 표 이름·열은 `pgTest` 전에 정한다. 머지된 번호라면 고치지 말고 새 번호를 쓴다(위 "머지된 마이그레이션은 고치지 않고").

## 응답에 새 필드를 더했더니 다른 사람의 계약 테스트가 깨졌다 (2026-11-03, PR 번호는 머지 때)

- 상황: 퀴즈 풀기 응답에 평가 개념 출처 `conceptSource`를 더하자 `QuizApiTest`의 "풀기 화면에는 정답·해설이 없다"가 실패했다.
- 원인: 그 테스트는 응답 글 전체에 `"concept"`라는 글자가 없는지 본다(문제별 개념 힌트를 막는 계약). 필드 이름에 그 글자가 들어갔다.
- 해결: 팀원 테스트는 고치지 않고 필드 이름을 `topicSource`로 바꿨다. 값(material/course)과 뜻은 그대로다.
- 다음에는: 풀기 응답(`QuizResponse`)에 필드를 더하기 전에 `QuizApiTest`의 금지 단어(correct, aiExplanation, 해설, concept)를 먼저 본다.

## 저장 직후 응답의 시각이 다시 읽은 값과 달라 Linux CI에서만 테스트가 깨진다 (2026-11-05, #123)

- 상황: 개념 학습 완료 API의 `firstCompletedAt`을 두 번 비교하는 테스트가 macOS에서는 통과했는데 CI(`build-and-test`, `postgres-test`)에서만 실패했다.
- 원인: Linux의 JDK 17은 `Instant.now()`가 나노초까지 나오고, DB 열(`TIMESTAMP(6)`)은 마이크로초까지만 저장한다. 저장 직후 응답은 메모리의 나노초 값을, 다시 읽은 응답은 잘린 값을 준다. macOS는 시계가 마이크로초라 차이가 안 보인다. 테스트 시계 `MutableClock`에 나노초를 더해 로컬에서 재현했다.
- 해결: 엔티티에 넣는 시각을 `LocalDateTime.now(clock).truncatedTo(ChronoUnit.MICROS)`로 DB 정밀도에 맞췄다.
- 다음에는: 저장 직후 응답으로 시각을 돌려주거나 비교하는 코드는 마이크로초로 자른다. CI에서만 깨지면 OS별 시계 정밀도부터 의심한다.

## 키를 넣었는데 퀴즈가 설정한 첫 모델이 아닌 다른 모델로 만들어진다 (2026-11-05, #132)

- 상황: LLM 키 3개를 넣고 퀴즈를 만들자 `generatedBy`가 GPT가 아니라 Gemini였다. 로그에는 `REJECTED`, 다음 시도에는 "배점이 범위 밖이다"가 남았다.
- 원인: ① `.env`의 `OPENAI_MODEL` 값 끝에 탭이 붙어 있었다(설정값은 끝 공백을 지우지 않는다). ② Anthropic은 키가 아니라 크레딧 부족으로 400을 줬다. ③ 지시문의 "배점(points, 2~5)"을 GPT가 합계로 읽어 기준 하나에 1점을 줬고, 서버 검증(기준마다 2~5)에 걸렸다.
- 해결: 탭을 지우고, 지시문을 "기준 하나하나 2~5 정수, 합계 아님"으로 고쳤다(`quiz-gen-v4`). 서술형 퀴즈를 GPT가 3번 모두 통과했다.
- 다음에는: 실패한 모델은 다음 모델로 넘어가 화면에서 안 보이니 `generatedBy`와 로그를 본다. `REJECTED`면 제공사 오류 메시지를 직접 확인하고, 지시문의 숫자 범위는 검증 코드와 같은 단위로 쓴다.
