# 백엔드 교훈

> 초안: 커밋 기록과 `docs/backend-design.md`에서 정리했다. 주미 님이 확인하고 고치거나 더하는 곳이다.

## 머지된 마이그레이션은 고치지 않고 새 버전을 추가한다 (2026-10-27, #57)

- 상황: 공지 본문 컬럼을 추가해야 했다(`V3__add_notice_content.sql`).
- 원인: Flyway는 이미 적용된 `V*` 파일을 다시 검사한다. 파일을 고치면 이미 만든 DB와 맞지 않는다.
- 해결: 표 구조는 마이그레이션 파일로만 바꾼다. 적용된 `V*` 파일은 건드리지 않고 새 번호를 추가한다.
- 다음에는: 새 버전 번호는 둘이 겹치지 않게 미리 말한다(지금 다음은 `V4`). 로컬 DB가 꼬이면 지우고 다시 켠다.

## 앱 DB 계정과 마이그레이션 계정을 나눈다 (2026-10-25, 초기 환경 구축)

- 상황: 로컬 DB를 만들 때 계정을 어떻게 둘지 정했다.
- 해결: 앱 계정은 데이터 읽기·쓰기만 하고, 표 변경은 마이그레이션 계정만 한다(`application-local.yaml`).
- 다음에는: 운영 DB 호스팅을 고를 때 이 두 계정을 만들 수 있고, 표 만들기 권한이 막히지 않는지 확인한다.

## 역할은 토큰이 아니라 요청마다 DB에서 읽는다 (2026-10-27, #56)

- 상황: 관리자 전용 경로(`/api/admin/**`)를 만들었다.
- 원인: 토큰에 역할을 고정하면 역할을 바꿔도 이미 발급된 토큰은 그대로 통한다.
- 해결: 세션 확인(`SessionValidator`)이 살아 있는 세션의 역할을 함께 돌려주고, 인증 필터가 그 역할을 권한으로 쓴다. 역할을 바꾸면 같은 토큰도 바로 403이 된다(통합 테스트로 확인).
- 다음에는: 가입은 항상 `USER`이고 관리자는 DB에서 직접 지정한다(역할 변경 API 없음). 화면 숨김은 보안이 아니다.

## 공지 본문은 HTML로 해석하지 않고 글자 그대로 저장한다 (2026-10-27, #57)

- 상황: 관리자가 쓴 공지 본문을 사용자 화면에 보여 준다.
- 해결: 제목 100자·본문 5000자로 검증하고 앞뒤 공백을 지운 뒤, HTML로 해석하지 않고 글자 그대로 저장한다. 프론트도 글자로만 다룬다.
- 다음에는: 작성자는 요청 본문이 아니라 토큰의 사용자로 정하고 응답에는 내보내지 않는다. 작성자가 탈퇴해도 공지는 남도록 `ON DELETE SET NULL`로 두었다.

## MySQL에서 PostgreSQL로 옮길 때 H2 테스트를 지키는 법 (2026-10-30, #78)

- 상황: 10/28 멘토링 추천으로 DB를 PostgreSQL + pgvector로 바꿨다. 빠른 기본 테스트는 H2로 유지하고 싶었다.
- 원인: `CREATE EXTENSION vector`는 H2에서 실패한다. `AUTO_INCREMENT`·`DATETIME(6)`·`FROM DUAL`은 PostgreSQL 문법이 아니다.
- 해결: 공통 문법(`GENERATED BY DEFAULT AS IDENTITY`, `TIMESTAMP(6)`)으로 마이그레이션을 쓰고, H2는 `MODE=PostgreSQL`로 둔다. 확장 설치는 `db/vector/`로 분리해 local·prod 프로필의 Flyway `locations`에만 넣는다. `vector`는 슈퍼유저만 만들 수 있어 DB 준비 단계(스크립트·CI)에서 미리 설치한다.
- 예외: 이번에는 운영 DB가 없어서 마이그레이션을 Postgres 문법으로 다시 썼다("머지된 마이그레이션은 고치지 않는다"의 예외). 처음에는 V1~V3을 문법만 고쳤다가 10/31에 `V1` 하나로 합쳐 처음부터 다시 시작했다(#82). 각자 로컬 DB를 새로 만들어야 하고, 운영 DB가 생기면 이렇게 하지 않는다.
- 다음에는: 버전 번호를 `V0_1`로 두어야 나중에 추가하는 V2 이상과 순서가 꼬이지 않는다. 실제 DB 동작은 `./gradlew pgTest`와 CI의 `postgres-test`로 확인한다.

## 긴 글에 쓰는 정규식이 1MB 요청 하나를 몇 분 동안 붙잡는다 (2026-11-01, PR 전)

- 상황: 대화 가져오기 서버 개인정보 재검사에 프론트 `mask.ts`의 이메일 정규식을 그대로 옮겼더니, 메시지 20,000자 × 50개 테스트 하나가 283초 걸렸다.
- 원인: `[A-Za-z0-9._%+-]+@...`는 '@'가 없는 긴 영문·숫자 덩어리(코드, 붙여 넣은 글)에서 시작 위치마다 끝까지 읽고 되돌아가서 글 길이의 제곱만큼 돈다.
- 해결: 앞에 `(?<![A-Za-z0-9._%+-])`를 붙여 덩어리 맨 앞에서만 시작하고, `++`(되돌아가지 않음)로 바꿨다. 찾는 결과는 같다. 같은 글 1MB 검사가 0.5초 안으로 줄었다.
- 다음에는: 사용자 글 전체에 돌리는 정규식은 아주 긴 한 글자 반복(`"a".repeat(20000)`)으로 시간 테스트를 넣는다. 프론트 `mask.ts`의 같은 정규식도 브라우저에서 같은 문제가 날 수 있다.
