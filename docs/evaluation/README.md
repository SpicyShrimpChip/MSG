# 평가 준비: 세 모델 비교 실험과 사용자 테스트

작성: 2026-11-24. 이 폴더의 도구는 모두 **읽기 전용 SELECT와 오프라인 계산**이다. AI를 새로 부르지 않고 DB를 바꾸지 않는다. 결과가 없는 상태에서 수치를 만들지 않는다.

| 파일 | 용도 |
|---|---|
| `model-judgments-export.sql` | 저장된 대화 분석 결과를 개념·모델 한 줄씩 내보내기 |
| `model_agreement.py` | 내보낸 결과 + 사람 정답표로 지표 계산 (표준 라이브러리만) |
| `test_model_agreement.py`, `sample/` | 계산 확인용 가상 예시와 테스트 (`python3 -I docs/evaluation/test_model_agreement.py`) |
| `user-test-metrics.sql` | 테스트 계정별 객관 지표(사전·사후 점수, 기능 사용 수) 집계 |

## 1. 세 모델 비교 실험

목적: GPT·Claude·Gemini를 함께 쓰는 방식이 단독보다 나은지 확인한다. **모델끼리 같은 의견이라는 것만으로는 정확하다고 보지 않는다.**

1. **사례 모으기:** 사용자 테스트 중 동의한 참여자의 분석 결과(이미 저장됨)를 쓴다. 새로 분석하려면 비용을 먼저 계산한다: 분석 1번 = 모델 최대 3번 호출, 사용자별 하루 10번, 서비스 전체 하루 500번 상한(`AI_DAILY_CALL_LIMIT`).
2. **정답표 만들기:** 개념마다 사람이 대화 원문을 보고 `understood / partial / not_understood / insufficient_evidence` 중 하나를 정한다(`labels.csv`: `run_id, concept_key, expert_status`). 판단 기준은 `AnalysisPrompt`의 규칙과 같게 하고, AI 판단을 보기 전에 정한다. 가능하면 두 사람이 따로 정하고 다르면 합의한다. 정하지 못한 개념은 비워 둔다(계산에서 빠진다).
3. **내보내기:** `model-judgments-export.sql`을 읽기 계정으로 실행해 CSV로 받는다(대화 원문·이메일은 나오지 않는다).
4. **계산:** `python3 -I docs/evaluation/model_agreement.py judgments.csv labels.csv`

| 지표 | 정의 |
|---|---|
| 모델별 기준 일치율 | 그 모델이 판단한, 정답표가 있는 개념 중 전문가와 같은 비율 |
| 다수 의견 기준 일치율 | 다수 의견(전원 일치·다수)이 있는 정답표 개념 중 전문가와 같은 비율 |
| 모델 간 불일치율 | 2개 이상 모델이 판단한 개념 중 의견이 모두 다른 비율 |
| 판단 보류율 | 다수 의견이 "근거 부족"인 비율 |
| 근거 검증 실패율 | 모델이 든 근거 중 서버 검증(보낸 메시지·말한 사람)에서 버린 비율 |
| 모델 호출 실패율 | 부른 호출 중 실패·형식 오류 비율 |

**보고할 때:** 비율과 분모(표본 수)를 함께 쓴다. 표본이 작으면 "경향"으로만 말한다. 선행연구의 정확도 향상 수치를 이 서비스의 성능처럼 쓰지 않는다. 지시문 버전이 다른 결과(v1·v2)는 섞지 않는다(`prompt_version` 열).

## 2. 사용자 테스트 설문: 외부 도구 vs LMS 내부

| | 외부 설문 도구(구글 폼 등) | LMS 안에 구현 |
|---|---|---|
| 개발 부담 | 없음 | 표·화면·API·테스트, 제출 직전 큰 변경 |
| 시연 위험 | 없음 | 운영 주소가 머지 때 바로 바뀐다 |
| 개인정보 | 응답에 이름·학번을 받지 않게 문항을 짜면 됨 | 계정과 응답이 바로 묶여 더 조심해야 함 |
| 객관 지표와 잇기 | 참여 코드로 운영자가 합친다 | 자동 |

**결정(11/24): 외부 설문 + LMS 객관 지표 집계.** 설문 문항(P1~P5, T1~T5, S1~S15, A·B·C1~3, E1~E5)은 이미 작성되어 있어 그대로 쓴다.

### 계정과 응답 잇기 (이름·학번·연락처를 받지 않는다)

1. 운영자가 참여자마다 테스트 계정을 만든다(예: `p01@…` 같은 임의 이메일). 실제 이메일을 받지 않는다.
2. 참여자에게 계정과 **참여 코드**(P01 등)만 준다. 설문 첫 문항에서 참여 코드와 집단(A 1학년 시험 준비 / B 3·4학년 취업 준비 / C 현직 실무자)을 고르게 한다.
3. 참여 코드 ↔ user_id 연결표는 운영자 PC에만 둔다. `user-test-metrics.sql` 결과와 설문 응답을 참여 코드로 합친 뒤 연결표는 지운다.

### 집계할 객관 지표 (`user-test-metrics.sql`, 서버가 센 값)

- 과제 수행: 자료 업로드, 요약 생성, 대화 가져오기, 분석 실행, 자료 기반 퀴즈, 확인 퀴즈, 학습 완료 개념 수
- 학습 전후: 최신 사전평가·사후평가 점수/만점(채점이 끝난 답만). 사후평가는 사전평가와 같은 개념·유형·문항 수라 비교할 수 있다(`AssessmentService.compare`의 비교 가능 조건 참고).
- AI 실제 사용 여부: 위 기능 사용 수가 0보다 큰지

### S12~S15를 확인할 객관 자료

| 문항 | 함께 볼 객관 자료 |
|---|---|
| S12 커리큘럼이 자료와 연관되는가 | 커리큘럼 개념 출처(자료에서 뽑은 개념 vs 과목 키워드), 학습 완료 개념 수 |
| S13 퀴즈가 자료 핵심을 반영하는가 | 자료 기반 퀴즈 수, 문제별 근거 검증 상태(원문과 일치·일부·실패) 분포 |
| S14 기존 AI 채팅보다 자료 관리가 효율적인가 | 자료·요약·퀴즈 사용 수 (주관 응답과 나란히, 인과로 말하지 않는다) |
| S15 AI가 판단한 취약 개념이 실제 어려운 개념과 맞는가 | 개념 검증 상태의 `quizComparison`(AI 판단과 확인 퀴즈가 같은 방향/반대) 분포. 위 1의 정답표 일치율과 함께 |

**통계 기준:** 집단별 n을 먼저 적는다. 사전→사후 차이는 같은 사람의 짝지은 값으로 본다(n이 작으면 기술 통계만). 응답이 없는 문항은 빼고 센다. 수치는 실제 응답으로만 만든다.

## 3. AWS 데모 테스트 준비 (리소스는 바꾸지 않았다)

이 브랜치에서는 AWS 리소스를 만들거나 바꾸지 않았다. 배포 전에 팀이 확인할 것:

- **V5 마이그레이션(`V5__evidence_based_learning.sql`):** 열 추가와 새 표만 있다. 배포 전 DB 백업(매일 백업 7일, `docs/deploy.md`)을 확인한다.
- **자료 기반 퀴즈·요약을 쓰려면** `MATERIAL_CONTENT_ENABLED=true`가 필요하다. 처리방침 7·8번(제공사·국가·보관 기간)과 처리 근거를 팀이 확정한 뒤에만 켠다. 꺼져 있으면 두 기능 모두 403과 안내 문구를 준다.
- **비용:** 요약은 자료·목적마다 한 번만 부르고 다시 쓴다. 상한은 `summary-daily-limit`(10), `daily-model-call-limit`(150), `AI_DAILY_CALL_LIMIT`(500). 예산(약 $200, 2주)에 맞는 값은 제공사 콘솔 단가와 실제 토큰 수(`quiz_ai_call`·`analysis_model_result`의 input·output tokens)로 팀이 정한다. 단가를 추정한 숫자는 여기 적지 않는다.
- 실제 모델로 확인할 것: 퀴즈 v6(인지 수준·근거 인용 형식), 분석 v2(행동 분류), 요약 지시문의 형식 준수율. 가짜 모델 테스트로는 확인할 수 없다.
